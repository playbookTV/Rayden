# Rayden UI review — September 19, 2026

Rayden has a restrained, coherent foundation, but accessibility and preview fidelity need attention before visual embellishment. For the confirmed audience of broad product teams, the largest opportunity is to make the library easier to evaluate and safer to adopt.

- Visually inspected the deployed Introduction, Button, Input, and Modal documentation. Examined desktop rendering at 1280 × 720 and Input at 390 × 844. Typed into the mobile input successfully and restored the browser viewport afterward.
- Read current local Button, Input, Select, Tabs, Modal, theme, and documentation preview source. Live deployment revision was not matched to the checkout; findings distinguish live observations from source findings.
- This is a sampled review, not a complete component, screen-reader, browser, or WCAG audit. Local application dependencies were absent; no local build or application test suite was run.
- Graph evidence used Verify tier, project `Users-leslieisah-app-dev-Rayden`, generation `2026-09-19T20:00:29Z`. Exact evidence paths were checked. Documentation is excluded from the graph and was read directly; theme CSS has parse gaps at lines 4 and 6 and was also read directly. Coverage is best effort.

## Anti-pattern verdict

The inspected pages feel like conventional developer documentation, without prominent decorative gradients, neon effects, or excessive animation. The orange accent gives some identity. The main weakness is repetitive presentation: oversized preview boxes and long lists make a simple library feel more laborious to browse. A familiar typeface is not itself a reason to redesign a calm product-team interface.

An independent Impeccable 3.1.0 source-pattern scan returned zero findings across `src/components` and `packages/docs/components` (82 TSX markup files and 37 supporting TS files). ## Priority findings

### P1 — Button labels lack sufficient contrast

The live Basic button uses white 14px text on `#f77a4a`, a contrast ratio of **2.68:1**. Current local light-theme primary styling gives white on `#eb5017`, **3.69:1**. The local Warning and Info variants calculate to **2.10:1** and **2.76:1** respectively. These are active controls, not disabled examples.

Normal-sized text requires at least 4.5:1 under [WCAG 2.2 SC 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html). The ratio calculations use the sRGB relative-luminance formula.

Use semantic foreground/background pairs with enough contrast in both themes and all interaction states. Preserve the orange identity by adjusting the relevant fill or foreground. Suggested workflow: `/audit`, then `/colorize`.

Evidence: `src/components/Button/Button.tsx:27`, `src/styles/globals.css`, and the live [Button documentation](https://rayden-docs.vercel.app/components/button).

### P1 — Dark previews render a light canvas

On the live Button page, explicitly choosing Dark produces a canvas whose computed background is `rgb(249, 250, 251)`. The selected Auto toolbar label is also nearly invisible against its pale surface in the observed dark documentation theme.

The source explains the mismatch: Preview chooses `bg-grey-900` for dark mode, while the global `.dark` token overrides make grey-900 nearly white. Other toolbar classes combine explicit dark variants with the same inverted palette. A Light choice under a dark ancestor also lacks an isolated light token scope.

Choose one consistent theme strategy, use semantic surface/text tokens, and isolate each preview's theme. Expose the selected theme through `aria-pressed` or equivalent semantics. Suggested workflow: `/audit`, then `/polish`.

Evidence: `packages/docs/components/Preview.tsx:54`, `packages/docs/components/Preview.tsx:61`, and `.dark` overrides in `src/styles/globals.css`.

### P1 — Modal focus behavior does not match the documentation

The local Modal implementation handles Escape and body scroll locking, but contains no initial focus, focus trap, background inertness, or focus restoration logic. It renders a normal portalled `div` with dialog attributes; those attributes alone do not manage focus. The documentation explicitly promises that focus stays inside the modal.

This is a source-confirmed implementation gap, not a live keyboard reproduction: the inspected Modal documentation page contains code examples rather than an interactive modal demo.

Implement and test opening focus, Tab/Shift+Tab containment, Escape dismissal, and return to the trigger. Add a live demo and keep documentation aligned with tested behavior. Suggested workflow: `/audit`.

Evidence: `src/components/Modal/Modal.tsx:119`, `src/components/Modal/Modal.tsx:167`, `packages/docs/content/components/modal.mdx:142`.

### P2 — Small examples consume too much vertical space

Every Preview uses a 400px minimum canvas height. A 36px button therefore occupies an entire large panel; the same pattern makes the phone-sized Input page require substantial scrolling between a simple example and its code.

Use compact, content-sized previews for controls and reserve larger canvases for layouts. Keep related variants close enough to compare. Suggested workflow: `/layout`.

Evidence: `packages/docs/components/Preview.tsx:101`; desktop Button and mobile Input observations.

### P2 — The introduction prioritizes implementation claims over evaluation

The first desktop viewport shows eight feature bullets and a long component navigation list; Quick Start begins near the bottom. There is no rendered product example in that first view. This serves developers who already know what they need better than a broad team deciding whether Rayden fits a product.

Place one representative composed example near the introduction, followed by clear routes to explore components and start building. Group navigation by task while preserving an alphabetical reference. Retain technical details lower on the page. Suggested workflow: `/distill` and `/clarify`.

Evidence: `packages/docs/content/index.mdx:8` and the live [Introduction](https://rayden-docs.vercel.app/).

## Cognitive load and audience walkthrough

The introduction has three concerns on the eight-item critique checklist: overly long chunks, too many simultaneous navigation choices, and weak progressive disclosure. Grouping, heading hierarchy, and keeping reference context visible work reasonably well. This suggests moderate cognitive load; it is a qualitative assessment, not a user-test result.

- **First-time evaluator:** encounters implementation benefits before seeing a composed result. A compact product example would build confidence sooner.
- **Keyboard or low-vision user:** small button labels have insufficient contrast; a modal consumer cannot rely on the advertised focus containment.
- **Mobile user:** can enter text, but oversized preview canvases separate examples from explanations and increase scrolling.

The emotional tone is restrained and orderly. Theme mismatches and unsupported accessibility promises undermine confidence at the point where a team evaluates trust. No complete task-completion or destructive-action journey was exercised, so peak/end experience remains unassessed.

## Recommended order

Address modal keyboard behavior and button contrast first, repair preview theming next, then compact the examples and improve the introduction. Finish with `/polish` after behavior and readability pass review.

## Implementation follow-up — September 20, 2026

All five priority findings have been addressed in the local checkout:

- Buttons use dedicated action colors with readable white labels in both themes, plus clearer outlined and keyboard-focus treatments.
- Preview canvases now isolate light and dark palettes, expose their selected theme to assistive technology, and use a compact 128px minimum height instead of 400px.
- Modal uses a native modal dialog for background inertness, contains keyboard focus, restores focus to the trigger, and respects Escape/backdrop dismissal settings. Portalled dialogs inherit their preview theme. Live examples now demonstrate these behaviors.
- The introduction leads with a working project checklist and editable project name, followed by routes for exploring components, using blocks, and adjusting design tokens. Technical setup remains available below.
- Repository edit links, the misleading input example label, and component-count metadata were corrected.

Validation passed: library type checking and production build; documentation production build (52 pages); lint on changed source and documentation components; and 22 focused Button/Modal Storybook tests. Tests cover computed contrast for six solid variants in both themes, focus containment and return, and dismissal settings. The browser tests used an already installed Chromium executable through a temporary configuration because the project's expected browser download stalled; that temporary configuration was removed afterward.

Manual checks against the local production preview confirmed dark and isolated light canvases, Tab/Shift+Tab wrapping, Escape dismissal with focus restoration, and editing/saving the project name. The introduction and edit dialog fit a 390 × 844 viewport without horizontal overflow. Viewport and theme preferences were restored after inspection.

This follow-up verifies the changed flows; it is not a full component-library, screen-reader, or cross-browser accessibility audit. The historical review scores and CSV counts above have not been re-scored. Changes have not been committed or deployed.
